The API call timed out. Did the real-world action already happen?

If an AI agent retries blindly, it may duplicate a payment, deployment, message, permission change, or other external effect. If it simply reports failure, it may erase an effect that already happened. RPOS keeps that uncertainty explicit and keeps authorization, dispatch, external-effect verification, repair, resumption, Human Return, and Responsibility Routing connected as executable responsibility-bearing state.

If the effect is unknown, responsibility must not disappear.

The problem

A successful API response is not the same thing as a verified effect.

Unknown stays unknown

If an external action may have happened but cannot be verified, RPOS does not silently convert ambiguity into success, failure, or automatic replay.

Receipt is not reality

A transport or tool receipt is kept separate from independent external-effect verification. Dispatching a request does not prove the outside world changed.

Routing is not Authority

Human Gate, reconciliation hold, repair, and return-for-authorization are distinct bounded routes. Choosing a route does not grant execution Authority.

Independent lineage

RPOS is the operating layer of the Responsibility Pathway lineage.

Responsibility Pathway means treating responsibility as a connected path across judgment, authorization, execution, external effect, uncertainty, repair, return, resumption, routing, and residual ownership — not as one approval flag or one audit record.

RPOS is independently engineered through Responsibility Pathway Model / Paper → Design → Engineering → Runtime → Operating System.

RPOS owns operation, not intelligence. Models are replaceable proposal sources; a proposal does not become operational authority merely because a model produced it.

Project identity

  • the project has its own documented Responsibility Pathway lineage;
  • its runtime and formal artifacts are inspectable in this repository;
  • public claims are grounded in RPOS implementation and reviewable evidence;
  • third-party names, institutions, standards, patents, or media do not transfer authority or proof to RPOS.

Core lifecycle

Responsibility is a path, not a flag.

PROPOSED→AUTHORIZED / HUMAN_GATE→DISPATCHING→VERIFIED / EFFECT_UNKNOWN→COMPLETED / REPAIR_REQUIRED / ROUTE

Lean 4 Formal Assurance Surface

Six published responsibility invariants are machine-checked and cross-linked to Python runtime tests.

RPOS machine-checks named structural properties including: Human Gate cannot dispatch directly; only VERIFIED may enter COMPLETED; EFFECT_UNKNOWN is not completion; READY_TO_RESUME is not authority; a receipt is not external-effect verification; and a model proposal is not operational authority.

Proof ceiling

  • the named invariant holds in its declared Lean model;
  • corresponding Python behavior is independently exercised by linked tests;
  • formal proof is not automatic proof of the complete runtime, deployment, legal responsibility, or organizational Authority.

Evidence boundary & promotion

Public Alpha is a current evidence state, not a permanent disclaimer.

RPOS separates evidence-limited boundaries that can move from permanent responsibility boundaries that software should not cross by itself. Stronger claims require declared evidence and review.

See promotion criteria

Permanent responsibility boundaries

  • software does not create legal or organizational authority;
  • a receipt is not proof of external effect;
  • route selection is not Authority grant;
  • governing a pathway does not make a third-party system correct;
  • abstract formal proofs do not automatically prove the complete runtime or deployment.
