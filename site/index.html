Keep authority, evidence, effect, and human responsibility connected.

RPOS is a Python operating layer for consequential software actions. It keeps the responsibility pathway explicit before dispatch, through uncertainty, across restart, and back to an authorized human when the effect cannot be safely concluded.

The problem

A successful API response is not the same thing as a verified effect.

Authority is contextual

RPOS binds authorization to the actor, operation, action, evidence, context, time, target, and exact effect instead of treating permission as a timeless boolean.

Unknown stays unknown

If an external action may have happened but cannot be verified, RPOS does not silently convert ambiguity into success or automatic replay.

Recovery preserves ownership

Restart and reconciliation retain the unresolved pathway and return it to repair or a Human Gate instead of erasing responsibility.

Core lifecycle

Responsibility is a path, not a flag.

PROPOSED→AUTHORIZED / HUMAN_GATE→DISPATCHING→VERIFIED / EFFECT_UNKNOWN→COMPLETED / REPAIR_REQUIRED / HUMAN_RETURN

Formal Assurance Surface

Machine-check the boundary, then show the proof ceiling.

RPOS turns Lean 4 into a user-visible assurance layer. The deployed viewer is generated from the exact site commit after a pinned lake build, and cross-links each operational risk to its Lean theorem, executable Python evidence, source hashes, model scope, and proof ceiling.

Assurance is not authority

  • Lean evidence never authorizes an operation;
  • formal proof does not approve a Human Gate;
  • abstract theorems do not validate an external effect;
  • runtime tests and operational evidence remain separate evidence layers;
  • every displayed assertion carries an explicit proof ceiling.

Evidence boundary & promotion

Public Alpha is a current evidence state, not a permanent disclaimer.

RPOS separates evidence-limited boundaries that can move from permanent responsibility boundaries that software should not cross by itself. Production-readiness, broader platform support, implementation-wide formal conformance, software-supply-chain trust, and domain-effectiveness claims can advance only when their declared evidence criteria are met and reviewed.

See promotion criteria

Permanent responsibility boundaries

  • software does not create legal or organizational authority;
  • a receipt is not proof of external effect;
  • governing a pathway does not make a third-party system correct;
  • arbitrary external systems cannot receive a universal exactly-once guarantee without the required contract;
  • abstract formal proofs do not automatically prove the complete runtime or deployment.
