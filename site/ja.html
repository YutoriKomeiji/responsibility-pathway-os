Open Source Python/SQLite runtime · Lean 4 bounded formal assurance · 0.1.0a2 Published Public Alpha

API実行後に通信が切れた。現実では、もう処理されているかもしれない。

ここでblind retryすれば、二重決済、二重deploy、二重通知、権限変更の重複などが起きるかもしれません。反対に「失敗」と閉じれば、すでに起きた現実の変更を見失うかもしれません。RPOSは、この「分からない」を成功・失敗・再実行のどれかへ勝手に潰さず、承認、dispatch、外部作用検証、修復、明示的再開、Human Returnまでを責任を伴う実行状態として保持します。

分からないとき、責任まで消してはいけない。

課題

APIが成功を返したことと、現実の外部作用が検証されたことは同じではない。

不明は不明のまま

外部作用が起きた可能性はあるが検証できない場合、成功・失敗・自動再実行へ勝手に変換しません。

応答は現実の証明ではない

transport/toolのreceiptと、外部systemを読み直して確認したeffect verificationを分離します。要求を送っただけでは現実が変わったとは断定しません。

回復後も責任を保持

restartやreconciliation後も未解決経路を保持します。repair readinessを実行権限へ自動昇格せず、明示的再開またはHuman Returnへつなぎます。

Independent lineage

責任経路とは、承認フラグではなく、判断から現実の作用まで続く経路です。

Responsibility Pathwayは、judgment、authorization、execution、external effect、uncertainty、repair、return、resumption、residual ownershipを切断せずに扱う考え方です。RPOSは、その考え方を実行可能なoperating layerへ落としたOpen Source実装です。

RPOSは、Responsibility Pathway Model / Paper → Design → Engineering → Runtime → Operating Systemという独自の開発lineageから構築されています。

RPOS owns operation, not intelligence. Modelは交換可能なproposal sourceであり、modelが提案しただけではOperational Authorityになりません。

Project identity

  • RPOSには公開された独自のResponsibility Pathway lineageがある
  • runtimeとformal artifactはこのrepositoryで直接検査できる
  • RPOSはGhostDrift Mathematical Instituteによる開発物・関連プロジェクト・同組織の実装ではない
  • 第三者の企業・制度・規格・特許・メディアの権威はRPOSへ自動的に移転しない

Core lifecycle

責任はフラグではなく経路。

PROPOSED→AUTHORIZED / HUMAN_GATE→DISPATCHING→VERIFIED / EFFECT_UNKNOWN→COMPLETED / REPAIR_REQUIRED / HUMAN_RETURN

2つのデモsurface、2つのevidence class

状態遷移を確認した後、actual RPOS runtimeをexternal-effect fixtureに対して実行する。

ブラウザデモは、公開済みRPOS lifecycleに基づく状態遷移simulationです。Python runtimeそのものをブラウザ内で実行しているとは主張しません。これとは別に、current source treeにはshipped RPOS serviceを呼び出し、RPOS状態をSQLiteへ永続化し、別SQLite external-effect storeを持つ別localhost HTTP processと通信し、実process restart、reconciliation、repair/resume、Human Gate denyを通すproduction-grade operational demo suiteがあります。

production-grade demo suiteは、公開済み0.1.0a2 wheel/sdistの公開後にmainへ追加されました。current-sourceのexecutable evidenceであり、既に公開済みのpackage artifactへ含まれるとは主張しません。

Lean 4 Formal Assurance Surface

6つの公開責任不変条件をmachine-checkし、Python runtime testへcross-link。

現在の公開assertionは、Human Gateから直接dispatchできない、VERIFIEDだけがCOMPLETEDへ入れる、EFFECT_UNKNOWNは完了ではない、READY_TO_RESUMEはauthorityではない、receiptはexternal-effect verificationではない、model proposalはOperational Authorityではない、の6件です。Viewerでは各riskからLean theorem、Python runtime evidence、source identity、model scope、proof ceilingまで辿れます。

Evidence boundary & promotion

Public Alphaは永久的な免責ではなく、現在のevidence stateです。

RPOSは、evidenceが揃えば前進できる境界と、software単体では越えるべきでない恒久責任境界を分離します。Production readiness、platform support、implementation-wide formal conformance、supply-chain trust、domain effectivenessは、宣言したevidence criteriaが満たされreviewされた場合にのみ昇格します。

長期目標は現在のalphaより大きいものです。AIを含む現実のworkflowで、責任を伴うoperational stateをより実行しやすく、検査しやすく、testしやすく、形式的に考察しやすく、修復しやすくし、責任を持つ人間・組織へ確実にreturnできるようにすることを目指します。これは方向であって、達成済みという断定ではありません。

昇格条件を見る

恒久的な責任境界

  • softwareは法的・組織的authorityを生成しない
  • receiptだけをexternal effectの証明にしない
  • 経路を管理してもthird-party system自体の正しさは生成しない
  • 必要contractを持たない任意外部systemへuniversal exactly-onceを保証しない
  • abstract formal proofだけでruntime/deployment全体を証明済みにしない
