Open Source Python/SQLite runtime · Lean 4 bounded formal assurance · 0.1.0a2 Published Public Alpha

API実行のあとで通信が切れた。そんなとき、無理に「成功」「失敗」を決めなくていい。

最初の要求で、外部systemはすでに変わっているかもしれません。だからといってすぐ再実行すると、二重決済、二重deploy、二重通知、権限変更の重複につながることがあります。RPOSは、結果が分からないときに無理に結論を出さず、必要な確認や人への引き継ぎまで責任経路をつないだままにします。

分からないときは、いったん分からないまま扱う。そのうえで、確認してから次へ進む。

RPOSが大切にすること

「APIが成功を返した」と「現実で処理された」は、同じとは限りません。

分からないときは、無理に決めない

外部作用が起きた可能性はあるものの確認できない場合は、いったんEFFECT_UNKNOWNとして保持します。勝手に成功・失敗・再実行へ進めません。

応答と現実の確認を分ける

transport/toolのreceiptと、外部systemを読み直して確認したeffect verificationを分けて扱います。要求を送ったことだけで現実が変わったとは判断しません。

途中で止まっても、続きが分かる

restartやreconciliationのあとも未解決経路を残します。修復の準備ができても、そのまま自動再開せず、必要に応じて人に確認してから次へ進みます。

Responsibility Pathway

責任を「一度の承認」ではなく、判断から現実の作用まで続く経路として扱います。

Responsibility Pathwayは、judgment、authorization、execution、external effect、uncertainty、repair、return、resumption、residual ownershipを切断せずに扱う考え方です。RPOSは、その考え方を実行可能なoperating layerへ落としたOpen Source実装です。

RPOSは、Responsibility Pathway Model / Paper → Design → Engineering → Runtime → Operating Systemという独自の開発lineageから構築されています。

RPOS owns operation, not intelligence. Modelは交換可能なproposal sourceであり、modelが提案しただけではOperational Authorityになりません。

RPOSの立ち位置

  • 独自のResponsibility Pathway lineageを公開している
  • runtimeとformal artifactをこのrepositoryで直接確認できる
  • RPOSの公開上の主張は、RPOS自身の実装・テスト・検証可能な証拠に基づいて示す

Core lifecycle

進めるときも、止めるときも、次に何を確認すればよいかが分かるように。

PROPOSED→AUTHORIZED / HUMAN_GATE→DISPATCHING→VERIFIED / EFFECT_UNKNOWN→COMPLETED / REPAIR_REQUIRED / HUMAN_RETURN

Lean 4 Formal Assurance Surface

大事な境界の一部は、Lean 4でも確認できるようにしています。

現在の公開assertionは、Human Gateから直接dispatchできない、VERIFIEDだけがCOMPLETEDへ入れる、EFFECT_UNKNOWNは完了ではない、READY_TO_RESUMEはauthorityではない、receiptはexternal-effect verificationではない、model proposalはOperational Authorityではない、の6件です。Viewerでは各riskからLean theorem、Python runtime evidence、source identity、model scope、proof ceilingまで辿れます。

ここで確認できる範囲

  • 宣言されたLean modelでnamed invariantが成立する
  • 対応Python behaviorは独立runtime testで確認する
  • theorem scopeとproof ceilingを公開catalogに保持する
  • formal proof・implementation evidence・external-effect evidenceは、それぞれ別の証拠として扱う

できること・まだできないこと

Public Alphaなので、今できる範囲を明確にしながら育てています。

RPOSは、evidenceが揃えば前進できる境界と、software単体では越えない恒久責任境界を分けて扱います。Production readiness、platform support、implementation-wide formal conformance、supply-chain trust、domain effectivenessは、必要なevidenceが揃いreviewされた範囲から段階的に前進させます。

長期目標は現在のalphaより大きいものです。AIを含む現実のworkflowで、責任を伴うoperational stateをより実行しやすく、確認しやすく、testしやすく、修復しやすくし、必要な場面では責任を持つ人間・組織へ確実にreturnできるようにすることを目指します。

詳しい昇格条件を見る

ここはきっちり分けます

  • softwareだけで法的・組織的authorityを生み出さない
  • receiptだけをexternal effectの証明にしない
  • 経路を管理してもthird-party system自体の正しさまでは保証しない
  • 必要contractを持たない任意external systemへuniversal exactly-onceを保証しない
  • abstract formal proofだけでruntime/deployment全体を証明済みとは扱わない
