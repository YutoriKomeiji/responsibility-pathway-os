API実行後に通信が切れた。外部処理は完了しているのか。

最初の要求によって、外部systemはすでに変更されている可能性があります。この状態で再実行すると、二重決済、二重deploy、二重通知、権限変更の重複につながることがあります。一方で、単純に「失敗」と判断すると、実際には発生済みの変更を見失う可能性があります。RPOSは、この不確実性を責任状態として保持し、必要な確認・修復・人への引き継ぎまで経路を維持します。

確認できないものを、確認済みとして扱わない。そのうえで、次に必要な判断へつなげる。

RPOSの役割

APIの成功応答と、現実世界での処理完了は分けて扱います。

不確実性を状態として保持

外部作用が発生した可能性はあるものの確認できない場合、EFFECT_UNKNOWNとして保持します。推測による成功・失敗判定や自動再実行には進みません。

応答と外部作用の確認を分離

transport/toolのreceiptと、外部systemを読み直して確認したeffect verificationを分けて扱います。要求を送った事実だけで外部作用を確定しません。

停止後も責任経路を維持

restartやreconciliationのあとも未解決経路を保持します。修復準備が整っても自動再開せず、必要な承認を確認してから次へ進みます。

Responsibility Pathway

責任を一度の承認ではなく、判断から外部作用まで続く経路として扱います。

Responsibility Pathwayは、judgment、authorization、execution、external effect、uncertainty、repair、return、resumption、residual ownershipを切断せずに扱う考え方です。RPOSは、その考え方を実行可能なoperating layerへ落としたOpen Source実装です。

RPOSは、Responsibility Pathway Model / Paper → Design → Engineering → Runtime → Operating Systemという独自の開発lineageから構築されています。

RPOS owns operation, not intelligence. Modelは交換可能なproposal sourceであり、modelが提案しただけではOperational Authorityになりません。

RPOSの立ち位置

  • 独自のResponsibility Pathway lineageを公開
  • runtimeとformal artifactをrepositoryから直接確認可能
  • 公開上の主張は、RPOS自身の実装・テスト・検証可能な証拠に基づいて提示

Core lifecycle

進行・停止のどちらでも、次に必要な確認と責任主体を明確にします。

PROPOSED→AUTHORIZED / HUMAN_GATE→DISPATCHING→VERIFIED / EFFECT_UNKNOWN→COMPLETED / REPAIR_REQUIRED / HUMAN_RETURN

Lean 4 Formal Assurance Surface

重要な責任境界の一部を、Lean 4で機械検証しています。

現在の公開assertionは、Human Gateから直接dispatchできない、VERIFIEDだけがCOMPLETEDへ入れる、EFFECT_UNKNOWNは完了ではない、READY_TO_RESUMEはauthorityではない、receiptはexternal-effect verificationではない、model proposalはOperational Authorityではない、の6件です。Viewerでは各riskからLean theorem、Python runtime evidence、source identity、model scope、proof ceilingまで確認できます。

対応範囲と境界

Public Alphaとして、現在の実装範囲と今後の拡張条件を明確にしています。

RPOSは、evidenceが揃えば前進できる境界と、software単体では越えない恒久責任境界を分けて扱います。Production readiness、platform support、implementation-wide formal conformance、supply-chain trust、domain effectivenessは、必要なevidenceが揃いreviewされた範囲から段階的に前進させます。

長期目標は現在のalphaより広いものです。AIを含む現実のworkflowで、責任を伴うoperational stateをより実行しやすく、確認しやすく、testしやすく、修復しやすくし、必要な場面では責任を持つ人間・組織へ確実にreturnできるようにすることを目指します。

詳細な昇格条件

責任境界

  • softwareだけで法的・組織的authorityを生み出さない
  • receiptだけをexternal effectの証明にしない
  • 経路を管理してもthird-party system自体の正しさまでは保証しない
  • 必要contractを持たない任意external systemへuniversal exactly-onceを保証しない
  • abstract formal proofだけでruntime/deployment全体を証明済みとは扱わない
