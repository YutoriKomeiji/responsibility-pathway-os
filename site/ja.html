API実行後に通信が切れた。外部処理は完了しているのか。

最初の要求によって外部systemはすでに変更されている可能性があります。この状態で再実行すると二重決済や二重deployにつながり、単純に「失敗」とすると発生済みの変更を見失う可能性があります。RPOSは不確実性を責任状態として保持し、確認・修復・再開・Responsibility Routingまで経路を維持します。

確認できないものを、確認済みとして扱わない。そのうえで、次に必要な判断へつなげる。

RPOSの役割

APIの成功応答と、現実世界での処理完了は分けて扱います。

不確実性を保持

外部作用が発生した可能性はあるものの確認できない場合、EFFECT_UNKNOWNとして保持します。

応答と作用の確認を分離

transport/toolのreceiptと、外部systemを読み直したeffect verificationを分けます。

RoutingとAuthorityを分離

Human Gate、reconciliation hold、repair、return-for-authorizationを別のbounded routeとして扱い、route選択だけで実行権限を生成しません。

Responsibility Pathway

責任を一度の承認ではなく、判断から外部作用まで続く経路として扱います。

Responsibility Pathwayは、judgment、authorization、execution、external effect、uncertainty、repair、return、resumption、routing、residual ownershipを切断せずに扱う考え方です。

RPOSは Responsibility Pathway Model / Paper → Design → Engineering → Runtime → Operating System というlineageのoperating layerです。

RPOS owns operation, not intelligence. Modelのproposalは、それだけではOperational Authorityになりません。

RPOSの立ち位置

  • Responsibility Pathway lineageを公開
  • runtimeとformal artifactをrepositoryから確認可能
  • public claimはRPOS自身の実装・Evidenceに基づく

Core lifecycle

進行・停止のどちらでも、次に必要な確認と責任経路を失わない。

PROPOSED→AUTHORIZED / HUMAN_GATE→DISPATCHING→VERIFIED / EFFECT_UNKNOWN→COMPLETED / REPAIR_REQUIRED / ROUTE

確認できるケース

  • 仕入先支払: 外部commit後に通信断 → 再起動 → 独立readback → 重複適用なし
  • 本番デプロイ: reject → repair → 再承認 → 独立verification
  • 特権アクセス削除: Human Gateで見送り → external side effect 0件

Lean 4 Formal Assurance Surface

重要な責任境界の一部をLean 4でmachine-checkしています。

Human Gateから直接dispatchできない、VERIFIEDだけがCOMPLETEDへ入れる、EFFECT_UNKNOWNは完了ではない、READY_TO_RESUMEはauthorityではない、receiptはexternal-effect verificationではない、model proposalはOperational Authorityではない、の6件を公開しています。

Proof ceiling

  • 宣言されたLean modelでnamed invariantが成立する
  • 対応Python behaviorは別のruntime testで確認する
  • formal proofだけでruntime全体・deployment・法的責任・組織Authorityを証明したとは扱わない

対応範囲と境界

Public Alphaとして、現在のEvidenceと昇格条件を分けて管理します。

RPOSはEvidenceが揃えば前進できる境界と、software単体では越えない恒久責任境界を分けます。

詳細な昇格条件

責任境界

  • softwareだけで法的・組織的Authorityを生成しない
  • receiptだけをexternal effectの証明にしない
  • route selectionはAuthority grantではない
  • third-party system自体の正しさまでは保証しない
